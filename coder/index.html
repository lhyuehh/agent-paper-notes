    CodeR 笔记¶

    论文 CodeR: Issue Resolving with Multi-Agent and Task Graphs 与仓库 NL2Code/CodeR。

    结论¶

    • 这里能用的只有轨迹数据。 仓库里的 trajs/ 是 261 条 SWE-bench Lite 上的完整运行记录，其余内容价值有限。
    • 论文思想不重要，没有根本创新。 它把现成的零件组装成了多角色流水线：命令集来自 SWE-agent，代码搜索来自 AutoCodeRover，用测试验证的思路来自 Aider，故障定位用的是几十年前的 SBFL。新的只是组装方式和"用 JSON 描述流程"。消融实验只在 50 道题上做，结论不强。
    • 仓库不含框架源码。 没有计划解析器、执行器和故障定位的实现，只有 5 份角色提示词配置，而且配置里的角色名与轨迹里的对不上。

    仓库里有什么¶

    内容 说明
    trajs/*.traj 261 条运行轨迹，合计约 90 MB
    logs/ 每题的评测日志
    all_preds.jsonl 每题最终提交的补丁
    results.json 评测结果：300 题中 82 题通过（README 写的是 85 题）
    config/roles/*.yml 5 个角色的提示词配置

    轨迹怎么读¶

    一个 .traj 文件顶层有四块：

    字段 内容
    environment 只有一个标签，如 "swe_main"
    trajectory 扁平的步骤列表，每步五个字段，见下
    history 全部对话消息，每条带 agent 角色标签，包含每个角色拿到的完整提示词
    info 最终补丁，以及整题的总 token 和费用

    trajectory 里每一步有五个字段：

    字段 内容
    thought 模型输出里，代码块之前的文字
    action 代码块里的那条命令
    observation 环境执行后的返回：文件窗口回显、搜索结果或终端输出
    response 模型的原话，等于 thought 加 action，重复存了一遍
    state 动作执行前的 shell 状态（打开的文件、工作目录）

    要点¶

    • 步骤里没有角色字段。 要还原是谁干的，只能数 succeed 或 fail（角色"交班"的信号），或者去 history 里按 agent 标签查。
    • 第一条 plan 的 observation 是回填的。 它是后面所有角色干完以后，四位同事的结论汇总，所以排在第 0 条，内容却是后面步骤的总结。
    • 角色的"结论"就是它交班前最后一段文字。 下游每个角色都会收到前面所有人的结论，不只是上一个人的。
    • 角色一上场，state 里的"当前打开文件"都被重置。 但磁盘上的文件不会重置。
    • 故障定位和相似题检索不是步骤。 它们是开局前算好的文字，直接写进提示词，轨迹里找不到计算过程。
    • 体积大头是文件窗口回显。 open、goto、edit 每次回显约 3000 到 4000 字。

    没有存的东西¶

    角色标签、路由决定、每步的耗时和花费、源码的中间版本。reproduce.py 的内容只能从回显里拼回来。

    使用时的坑¶

    • results.json 不是合法 JSON，数组末尾有多余逗号，json.load 会直接报错，需要先去掉。
    • 角色名不统一：论文叫 Fault Localizer、Editor、Verifier，轨迹和实际运行里叫 Debugger、Programmer、Tester。
    • 不要用轨迹里测试员的判定当成败标签。有的测试员只检查脚本不报错，改动前后输出一模一样也会判通过，应以 SWE-bench 的最终评测结果为准。
    • 重规划的轨迹更有分析价值：261 条里 27 条发生过重规划，经理会针对失败原因自己重写任务文字，不是照抄预设计划。另有 6 条因预算耗尽而强制结束。
